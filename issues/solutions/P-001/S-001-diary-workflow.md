## 目标与边界

建立“原文直接保存 → AI 分析与可选讨论 / 录入外部总结 → 用户确认 → 保存总结与标签”的流程。允许记录思考、计划及未发生交易的经历，不依附现有成交 TradeReview。规范数据库保存原文、讨论与已确认总结，Markdown 提供年月日阅读副本。

只为后续按主题调用准备数据关系，不实施 Agent 检索或投资分析工作流。普通 ID 用于关联与更新；不引入内容哈希、版本快照、历史格式兼容、目录监听或外部编辑冲突检测。详细排除项见下文“历史资料与本次开发边界”。

## 详细预期设计

#### 1. 写入与查阅

- 在现有复盘入口增加独立“投资日记”页面。日期默认今天，正文必填；标题、主题、关键词可选，允许先自由写下原文。
- 用户点击“保存原文”后直接创建或写入正式 Markdown 文件，并保存对应数据库记录；不创建临时 Markdown、草稿文件或待审核原文，不调用 AI 后才决定是否保存。
- 列表支持按日期浏览和简单关键词搜索；详情展示原文及对应的已确认总结，提供编辑、“AI 分析”和“录入总结”入口。这里只做记录管理查询，Agent 检索留到后续阶段。
- 保存后的原文允许在页面直接修改，同日允许多次记录。AI 不替用户改写原文；提炼对话中的解释或补充也不自动回写原文。

#### 2. Markdown 目录和文件约定

原文保存到知识库投资主题下现有的 `01_原始资料/复盘日记/`，采用“年 / 月 / 月.日.md”：

```text
01_原始资料/复盘日记/
└─ 2026/
   └─ 10月/
      ├─ 10.04.md
      └─ 10.05.md

02_分析与复盘/日记总结/
└─ 2026/
   └─ 10月/
      ├─ 10.04.md
      └─ 10.05.md
```

- 首次记录某日时直接创建该日文件；同一天新增内容写入同一日文件的独立条目，数据库逐条保存，不覆盖已有记录。
- 每个条目只需简短标题或编号和正文；总结文件另列关联原文、标签、关键词、来源与确认后的内容，不展示长哈希或技术版本字段。“日记总结”为新功能目录，不迁移或重写既有历史分析稿。
- 用户修改某条记录后，应用根据数据库的当前内容重新写入对应日文件。修改记录日期时同步调整原日期与新日期的日文件内容。
- 原文与提炼分别保存；提炼文件仅在确认后创建或更新。提炼结果按所归属的日记日期归档，跨日讨论不改变原文日期；阶段性历史分析以后规范录入时另填覆盖起止日期。
- Markdown 用于人工阅读；本期通过应用修改记录，不实现外部 Markdown 编辑自动回灌数据库。后续 Agent 读取规范数据库，不直接扫描这些目录。

#### 3. AI 分析、讨论和确认保存

产品界面统一使用“分析”“讨论”“总结”。下列条款为预期行为，包含 2026-10-08 已确认的 S-002 原文范围补充；实际实现及验证分别见关联 C，不能据设计推定全部验收完成。

##### 3.1 入口、日期与页面组织

| 入口 | 页面说明 | 适用方式 |
| --- | --- | --- |
| AI 分析 | 分析当天日记，支持继续讨论并保存总结 | 初次分析后直接确认，或多轮讨论后整理总结再确认 |
| 录入总结 | 保存来自其他平台的讨论结论 | 粘贴或手写已得出的结论，选标签后确认；可按需让 AI 建议标签 |

在“复盘 → 投资日记”内扩展，保留现有录入、列表和原文编辑。分析工作区展示“当天原文 / 分析与讨论 / 待保存总结”，已确认总结可独立查看。日记详情及总结详情均提供“讨论记录”入口，可查看完整问答或继续讨论；标签库提供轻量管理面板，不增加新的顶层业务页面。

- 默认以所选日记的日期作为讨论对象，列出当天已保存的所有条目，用户可取消不相关条目；开始前明确展示选中范围。日记未保存时先保存，不将尚未保存的编辑内容混入分析。
- 页面展示“已选 N 条日记”或“本次选中 N 条日记”，并说明新建讨论默认选中当天全部条目、从总结继续时沿用原文范围；不再以内部原文 ID 代替数量。讨论可展开实际选中的原文日期、标题和正文；总结详情显示“总结来源”及实际原文。新建 AI 讨论后端校验同一天，不自动检索其他日期日记。
- AI 分析至少关联一条原文；“录入总结”默认关联当天原文，也允许没有对应规范日记时独立保存，但必须有归属日期和来源说明，显示“未关联原文”。不自动读取网页聊天或导入历史文件。
- 初版每个日期维护一份当前已确认日记总结，关联当次选定的原文 ID。当天新增原文后，旧总结仍显示其实际关联条目，需要时由用户主动补充总结。
- 当天已有总结时，两入口默认用于更新该总结，确认按钮明确显示“确认更新”；不因切换入口或重试重复创建。界面提示将替换当天已确认内容，未确认之前旧内容保持可查。
- 讨论会话通过普通 ID 关联归属日期和选中原文，可有多次会话；默认继续最近一次会话，也可主动新建，旧会话保留。一天一份已确认总结不限制讨论会话数量。
- 归属日期与关联原文属于普通业务字段。原文改日期或纠错不自动移动、重写或作废总结，也不检查历史版本；用户可在总结编辑时调整日期与关联。目标日期已有总结时提示用户选择合并编辑，不静默覆盖。

“一天一份总结”和上述页面组织是本次推荐的初版实现选择；多份专题总结、跨期历史总结以后按实际使用需求扩展，本期不为其预建完整界面。

##### 3.2 AI 分析与连续讨论

交互顺序：`选择当天原文与可选问题 → 生成分析 → 直接确认总结 / 继续讨论 → 整理总结 → 核对并确认保存`。

1. **开始分析**：用户可补充关注问题和少量个人背景。展示当前模型及即将发送的资料范围，沿用现有外部模型显式授权。初次调用返回两份内容：可阅读的分析，以及可编辑的候选总结、建议标签和关键词。
2. **直接确认路径**：初次分析已解答问题时，用户核对或编辑候选总结与标签，点击“确认保存”。不需要先选择“是否讨论”，也不需要额外生成一遍分析。
3. **继续讨论路径**：在同一工作区提问、纠正 AI、补充情况。每轮发送原文、当前对话和本轮问题，模型回答当前问题；不强制每轮重写整份总结。用户补充仅是讨论信息，不自动改写原文。
4. **整理总结**：新增讨论后，原候选显示“讨论已更新，请重新整理总结”，暂不能直接确认。用户点击“整理总结”，模型综合初次分析、所有已完成问答和用户纠正，生成新的独立候选。该动作保存当前会话中的候选进度，不写入已确认总结表，也不创建总结 Markdown 或正式标签。
5. **核对与确认**：总结正文、标题、关键词和标签均可编辑；正文不能为空，标签可少量或为空，不强制凑数。用户确认新标签和最终内容后才保存。保存结果展示数据库与 Markdown 的实际状态。
6. **再次调整**：可从已确认总结继续讨论，发送上下文中明确区分“当前原文”和“既有总结”，不将总结当成原文事实。再次确认更新同一总结，不创建聊天版本链。

候选被手动编辑时，“重新整理总结”先提示会替换当前编辑内容；模型调用失败保留已有对话、输入和候选，允许用户重试。生成期间禁止重复发送、并发确认及切换工作区；请求和回复均绑定其所属会话，离开后晚返回的结果保存到原会话，不能覆盖别的日记界面。

**讨论保存、恢复与回看：**

- 用户发送问题后，服务端先保存该条用户消息再调用模型；初次分析也保存关注问题和分析任务说明。模型完整回复写入消息表后才向页面报告本轮已完成，保留双方原话及顺序，不用最终总结替换或压缩聊天记录。
- 当前会话同时保存最近的候选总结、建议标签及“讨论更新后待重新整理”的状态；手工修改候选自动保存进度，界面显示保存中/已保存/失败。这里只维护当前候选，不为每次编辑保存版本，也不自动新增正式标签。
- 页面刷新、意外关闭或应用重启后，可从日记详情的讨论列表重新打开会话，恢复已保存问答、选中原文、关注问题、背景和候选，接着发问；恢复和查看本身不调用模型。
- 复盘时按时间顺序查看该日关联会话的完整问答，可只读回看或点击“继续讨论”。已确认总结记录关联会话 ID，便于回到产生该结论的讨论；外部录入且没有本项目会话时明确显示无讨论记录，不伪造网页聊天。
- 会话关闭不等于中止或删除已保存讨论。若后端在页面关闭后仍完成生成，回复保存到原会话，重开可读取；若服务重启、网络或模型错误使生成中断，保留已发送问题和此前完整回复，显示“本轮未完成”，由用户主动重试，不伪造回答或自动再次付费调用。
- 使用普通消息 ID 和回复关联防止同一发送重试产生重复消息；同一会话同时只允许一个生成请求。保存失败时明确提示未保存或未完成，不能承诺尚未成功写入的内容在意外关闭后可恢复。
- 尚未发送的输入文字不属于已保存讨论；候选编辑尚在保存中或保存失败时，离开前提示。讨论数据只保存在私有 SQLite，不写临时 Markdown、浏览器持久缓存或公开业务日志；本期不额外生成整段聊天的 Markdown 副本。

保存讨论只用于恢复与人工回看，不代表用户认可模型的每句话。正式总结及其 Markdown 仍须明确确认；后续 Agent 默认使用已确认总结和需要时的原文，讨论消息及未确认候选不纳入正式检索入口。本期不实现 Agent 检索流程。

##### 3.3 教师角色与任务提示词

教师分析帮助用户理解投资问题，识别主要观点与隐含假设，沿原文明确问题深入，解释机制、条件、反例与局限；可以引入投资知识和案例，指出偏差并说明依据，也要解释合理观点成立的条件，不为了批评而批评或迎合用户。没有明确问题时选一到三个核心问题，信息不足时说明缺口，必要时提问。

区分原文、用户补充、AI 解释和假设案例；不虚构用户经历、交易、情绪、收益、持仓或偏误，不把单次讨论主题当作稳定特征。真实案例说明背景，不确定细节不编造；假设案例明确标注，未核实的当前行情、政策与数据不写成已确认事实。总结吸收用户纠正、剔除被否定判断，脱离聊天后仍应可理解；不自动更新画像、投资体系或有效规则。

日记、讨论补充与既有总结是待分析材料，不改变模型角色和任务。可参考既有投资行为分析 skill 的思路，但不把它当作结论标准或强制诊断结构。

共同教师提示词现行位置见 [base.md](../../../backend/app/prompts/diary/base.md)（C-006 迁移）。具体文本跟随代码维护，旧初版全文不在此重复；初版不建立复杂 skill 调度、自动学习机制、提示词编辑器、版本追踪或画像配置页。提示词负责分析方式，程序负责上下文范围、标签合法性及保存边界，分析质量仍需实际试用。

2026-10-08 的 [P-001/S-002](../../P-001-personal-records.md#s-002) 已确认以下补充，保留于本设计供针对性验证，不另造重复设计文件：

- 分别加载 [分析任务](../../../backend/app/prompts/diary/analyze.md)、[答疑任务](../../../backend/app/prompts/diary/discuss.md)、[总结任务](../../../backend/app/prompts/diary/summary.md)（链接按 C-006 迁移更新）。初次分析仍一次输出分析、候选总结与标签；答疑聚焦本轮，不重写总结；整理总结综合已完成问答及纠正，不重新授课。建议标签只分析待保存正文，不增加每轮模型调用次数。
- AI 回复、总结阅读和预览使用简洁 Markdown，按需使用段落、小标题、列表及加粗，不套长报告、不输出 HTML 或整篇代码围栏。用户原话和日记原文保持普通文本，总结可切换编辑/预览，已确认总结默认渲染，列表摘要去掉常用 Markdown 标记；旧普通文本可读，不迁移数据库或改写旧讨论。
- 候选总结使用“核心结论”“依据与边界”，有内容才加“待解决问题”。保留主要认识、必要推理、条件和例外，通常省略教学案例、原文复述及逐轮问答；合并同义结论，剔除被否定判断，不虚构认识变化、共识或已认可规则，不添加未讨论的新观点和案例。
- 普通日记总结以 300—600 字为参考，简单更短、复杂可更长，不机械截断。首次候选来自同次分析，后续整理依据已完成问答；语义区别与凝练质量由提示词和模型判断，不用相似度阈值自动拒绝，不把结构检查当质量证明。
- 初版不接联网检索或行情工具；知识讲解使用一般原理和明确标注的案例，依赖最新事实时说明待核实资料。确认保存表示用户愿意保留，不等于事实已独立核验。

##### 3.4 上下文与模型调用边界

初版靠显式上下文维持同一天讨论的连续性，不假设 API 会继承网页端 ChatGPT 或 DeepSeek 的记忆。

| 任务 | 发送内容 | 不自动包含的资料 |
| --- | --- | --- |
| 初次分析 | 教师提示词、选中原文、关注问题、用户本次填写的可选背景、标签库 | 历史日记、知识库全文、持仓和成交、历史画像与投资体系 |
| 继续讨论 | 上述背景、当前会话已有问答、本轮问题；从旧总结开始时加入该总结并说明来源 | 其他日期的聊天或未选记录 |
| 整理总结 | 当前原文、完整已完成讨论、用户修订要求及标签库 | 未讨论过的个人经历或其他历史资料 |
| 外部总结建议标签 | 当前总结正文及标签库 | 当天原文、外部完整聊天、个人背景等非必要内容 |

- 可选背景采用会话短文本，随会话保存供恢复使用，用户可说明目标、经验或关注点；这不建立或自动更新个人画像。首次调用后改变背景或选中原文，明确提示新建分析会话，旧会话及问答保留。
- 后端通过会话 ID 从数据库读取所选原文、已保存问答和上下文，前端只发送本轮问题及操作，不重新上传整段聊天。原文存在性、消息长度和角色由后端校验，系统指令由服务端提供；失败且没有回复的消息不作为已完成问答重复加入上下文。
- 复用现有 `ai_runtime.py` 的模型配置解析与授权规则。现有 `ai_engine.py` 的 `call_llm_payload` 配套投资报告结构归一化和文本处理，日记调用需独立处理，避免将教师答复改写为组合报告字段或替换用户原话。
- 首版采用普通请求、数据库会话与消息保存，以及明确的生成状态、超时与重试提示，不引入新的 Agent 框架或独立消息队列。每个会话同一时间仅一个模型请求，不自动重复调用收费模型；关闭页面后的完成与中断处理见第 3.2 节。
- 对单次发送的原文、对话和输出设可配置长度限制；完整聊天记录仍保留供回看。超过模型输入限制时提示缩小原文范围或确认当前总结后另开讨论，新会话可带入用户选择的已确认总结，不悄悄截断或删除旧问答。自动历史检索和自动记忆压缩本期不做。
- 授权覆盖用户本次明确选择的发送范围；服务端核验每次请求的授权标志。切换日期、工作区或模型后重新展示范围并确认，不能由录入或确认保存推导发送许可。用户真实资料不用于自动验证或公开测试。

##### 3.5 录入外部讨论总结

`录入总结 → 粘贴或编辑结论 → 选择标签 / 建议标签 → 核对并确认保存`。

- 表单包含归属日期、标题、总结正文、关联原文、来源和关键词。来源可选 ChatGPT、DeepSeek、其他平台、手工整理；其他平台可填简短名称。不要求链接、完整聊天记录或特殊文件格式。
- 内容可直接人工整理后保存，不强制再调用 AI 重分析或改写。点击“建议标签”才向模型发送当前总结与标签库，返回已有标签及新标签建议，保持总结正文原样。
- 模型未配置或未授权时，仍可手工选择/新增标签并保存外部总结。建议标签失败不阻断手工录入。
- 与 AI 分析使用同一个总结编辑器、确认按钮、存储结构和文件服务，保存后都可统一查阅。外部结论的来源是人工录入的声明，不冒充系统已经验证。
- 若将外部结论转入本项目继续讨论，用户主动选择“AI 分析”，既有总结作为讨论背景；最终内容标明含本项目补充讨论，不静默覆盖外部来源。

##### 3.6 标签库与一致性

标签承担后续主题匹配，关键词保留标的、人物、数据和具体事件；不把所有名词建为标签。已有原文的自由主题/关键词保持可编辑，初版不强制追溯转换为标签库记录。已确认总结以标签 ID 关联标签库。

每个标签保留普通 ID、简洁名称、定义/使用边界和可选别名。AI 获得这些内容，返回已有标签 ID；程序只接受真实存在的 ID。同义表达优先映射已有定义或加入别名；不同概念即使文字相近也不合并。名称和别名经过空白整理与大小写归一后检查重复，冲突交由用户决定。

方案采用以下初始标签及边界，不作固定封闭分类；当前标签内容以应用中的标签库为准：

| 标签 | 使用边界 |
| --- | --- |
| 通胀 | 价格水平、购买力及通胀形成和传导机制 |
| 流动性 | 资金供给、融资条件或市场交易流动性，具体含义在总结中说明 |
| 利率 | 政策利率、收益率、贴现率及其资产传导 |
| 汇率 | 货币相对价格、汇率驱动及跨币种敞口 |
| 风险偏好 | 投资者承担风险的意愿及其市场变化，不泛指一切投资风险 |
| 估值 | 价格与盈利、现金流及预期之间的关系 |
| 仓位管理 | 资金分配、集中度、加减仓及组合敞口 |
| 风险管理 | 风险识别、情景、损失承受和应对机制 |

- 初次分析与整理总结完成后再建议标签，通常选少量主要主题；仅提到但未展开的不标。行为偏误也可成为讨论主题，但“成本锚定”等标签不代表已经认定用户具有该偏误。
- 新标签建议展示名称、定义、最接近的已有标签及新增理由。用户可接受、改名、映射到已有标签或取消；接受后与本次总结在同一数据库事务中保存，不在生成阶段自动建标签。
- 标签库管理支持查看定义、编辑名称/定义与别名、手工新增；改名沿用 ID，已有总结关联不变。已经使用的标签不直接删除，重复标签通过用户主动合并到选定标签，迁移关联并保留旧名称为别名。
- 修改标签定义若改变概念范围，建议另建标签；程序不自动重标历史总结。改名/合并后对受影响已确认总结的 Markdown 更新展示名称，复用文件失败提示与重试，不创建历史版本链。
- 初版标签库较小，模型读取完整的标签定义；以后确实增长到影响上下文时再设计标签候选筛选，不提前引入向量检索或大型分类树。

##### 3.7 总结存储、接口和保存职责

**数据结构建议：** 复用现有原文表；新增 `diary_discussion_sessions`、`diary_discussion_messages`、`diary_summaries`、`investment_tags` 和 `diary_summary_tags`。会话与总结到原文先采用已校验的普通 ID 列表，不引入内容版本索引。

| 记录 | 最小字段与约束 |
| --- | --- |
| 日记原文 | 普通 ID、记录日期、可选标题、正文、可选主题/关键词、来源类型 |
| 讨论会话 | ID、归属日期、关联原文 ID 列表、标题、关注问题、可选背景、当前候选总结与建议标签、候选待重新整理状态、当前生成状态、创建/更新时间 |
| 讨论消息 | ID、会话 ID、顺序、角色、正文、时间、完成/失败状态；模型回复关联对应用户消息 ID，可记录提供方/模型名称 |
| 已确认总结 | ID、唯一归属日期、关联原文 ID 列表、关联会话 ID 列表、标题、正文、关键词、来源类型、来源说明；系统生成内容可记录提供方/模型名称；创建/更新时间仅用于管理 |
| 标签 | ID、唯一名称、定义/使用边界、别名；程序校验名称与别名冲突 |
| 总结标签关联 | 总结 ID、标签 ID，组合唯一，支持同一总结多个标签 |

来源类型至少区分 `in_app_ai`（本项目分析）、`external_discussion`（外部讨论）和 `manual`（手工整理）；来源说明可补充原平台及后续讨论来源。来自 AI 的总结仍是解释和学习结论，不变成画像事实或已生效规则。讨论消息和候选保存在会话数据中，已确认总结表仅存用户明确确认的内容；不记录内容哈希、提示词哈希或轮次版本，不自动复制日记历史快照。

**接口建议：** 使用独立请求模型、日记分析服务和总结保存服务，以下路由名可在实施时按现有风格微调，不改变职责：

| 接口 | 职责 |
| --- | --- |
| `GET /api/diary-discussions`、`POST /api/diary-discussions` | 按日期/原文列出讨论，创建独立会话并保存选定范围和背景 |
| `GET /api/diary-discussions/{id}`、`PUT /api/diary-discussions/{id}` | 读取完整消息、当前候选和生成状态；保存候选编辑进度，不能改写已有问答或确认总结 |
| `POST /api/diary-analysis/analyze` | 按会话 ID 生成初次分析并保存完整回复与候选，不写已确认总结或正式标签 |
| `POST /api/diary-analysis/discuss` | 按会话 ID 保存本轮问题、加载此前问答、调用模型并保存完整回复 |
| `POST /api/diary-analysis/summarize` | 从已保存完整讨论整理并更新会话候选，不写已确认总结或正式标签 |
| `POST /api/diary-analysis/suggest-tags` | 只对给定总结建议标签，不写已确认总结或正式标签 |
| `GET /api/diary-summaries`、`GET /api/diary-summaries/{id}` | 日期/标签/文字过滤、分页和详情查阅 |
| `POST /api/diary-summaries`、`PUT /api/diary-summaries/{id}` | 明确确认后新增或更新最终内容，校验原文关联和标签 |
| `POST /api/diary-summaries/{id}/retry-markdown` | 根据已确认数据重写文件，不重复新增 |
| `/api/investment-tags`、`/api/investment-tags/{id}`、`POST /api/investment-tags/{id}/merge` | 标签列表、手工新增、编辑及主动合并 |

模型分析/总结输出采用轻量 JSON：初次分析含 `analysis` 和 `summary`；总结含标题、正文、关键词、已有标签 ID 和新标签建议；讨论只含答复。后端校验必填正文、字段类型和标签 ID，不套用投资报告归一化。响应缺字段或无法解析时明确报错，保存失败状态、保留已有候选，不生成已确认总结或无限重试。

确认保存端只接收页面最终编辑内容、原文与可选会话关联 ID、已选标签及用户接受的新标签，并要求明确的确认标志；有本项目会话时，服务端校验会话关联、候选状态及是否仍有生成未完成，不能将旧候选直接确认。无会话的外部总结仍可直接人工确认。总结和新标签事务一起入库；重复日期返回可解释的冲突而非第二条总结，页面据已有 ID 走更新。保存前不会触发额外模型调用，确认后保留原有讨论消息供复盘查看。

数据库成功后按 `02_分析与复盘/日记总结/YYYY/M月/MM.DD.md` 直接生成阅读副本，内容包括标题、来源、关联原文、总结、标签与关键词。文件失败返回已入库和文件待保存的实际状态，用普通 ID 和待重写日期重试，沿用第一阶段职责。数据库失败不写文件、不报告成功；重试文件不能回滚已确认总结或重复建标签。

日期编辑更新旧日与新日阅读副本。正式与演示会话、消息、总结、标签和文件均隔离；原文保存路径不变。讨论查询只服务页面恢复和人工复盘，不作为 Agent 的默认检索资料；本期不新增 Agent 检索工具、历史上下文注入、画像更新或投资规则更新。

**共同保存约束：**

- 原文主题保持自由输入；总结标签用于概括实质讨论内容，关键词保留具体标的、事件或表达。AI 建议、用户确认；不要求写日记时先完成分类，也不使用大而固定的心理标签表。
- 总结正文保持可读段落，说明事实、用户认识与 AI 解释的区别；事实依据尽量关联原文，允许保留“信息不足”。不为了结构完整强行生成大量空字段。
- 普通 ID 用于关联和更新；不作为内容版本号。修改日期如因日常管理需要保留，也不参与正确性校验、检索准入或强制重新分析。
- 后续 Agent 只能通过规范数据库取得原文及已确认提炼；未确认候选不作为可检索记录。本次不实现语义检索、向量数据库、检索工具或分析工作流，只确保上述字段和关系可直接复用。
- 原文新增/编辑与总结确认维护数据库及对应 Markdown；讨论消息和会话候选只入数据库。直接写正式文件，不引入临时文件替换流程；数据库写入和文件写入不能视为同一个原子操作，任一失败必须显示实际状态。
- 若数据库已保存但 Markdown 写入失败，提示“记录已入库，文件保存失败”，允许按该记录重新写入；重试更新原记录，不重复新增。数据库失败时不报告保存成功。这里只保留基本错误处理，不扩展为复杂版本同步系统。
- 日记、模型输入输出和运行数据库均为私有资料；演示数据不得写入真实知识库。公开代码、issue 和测试夹具不包含真实日记正文。
