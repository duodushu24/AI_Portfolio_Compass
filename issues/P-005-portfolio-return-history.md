## 问题与目标

资产分散于多个账户，覆盖 A 股、港股、美股及场内/场外基金。目标是在本地系统记录全账户持仓、买卖、资金和价格，自动计算持仓成本、现金、已实现与浮动盈亏、账户总资产及累计账户收益。

首次确认期初数量、平均成本、现金、市值及日期；日常只记录买卖、资金变动和更新市值。每次业务记录由系统自动更新结果并保留历史，不要求用户分别录成交、修改持仓和另存收益。主图为全账户净值收益率，可查看账户盈亏金额；标的详情集中展示成本收益、交易及历史，清仓后仍可进入。

手工市价/净值或标的市值更新即可形成真实观察点，支持任意时点、同日多次和历史补录；记录实际报价时间。先完成手工闭环，稳定自动行情及 K 线不作前置。周复盘只是使用习惯，不固定记录间隔。

金融应用是功能体验参照，不保证不同平台的收益公式一致；本项目明确统一计算口径、起点、账户范围和准确/估算状态。

## 当前实现与缺口

依据 C-007 与本轮讨论中的源码/运行接口核对，不将规划当作已实现：

- 手工“记录新状态”已会追加历史，“纠正旧记录”修改指定旧行；完整/局部批次和作废状态已有基础。问题在于这些观察还没有与成交和现金形成统一账目。
- `Deal` 保存买卖，但未自动更新持仓与平均成本、结转卖出利润和现金；当前需分别维护事实。
- 收益观察固定保存价格，但不会同步持仓表采用的价格；总览、持仓和收益图有多条计算/读取路径，需集中。
- 标的详情仍依赖当前持仓，清仓标的无法使用同一详情入口；历史收益另放在独立面板。
- 完整账户现金与资金流调整后的净值收益尚未实现。旧交易复盘的成交后价格表现不等于已实现盈亏。真实行情和 K 线问题未解决。

## 关键讨论结论

- **用户已确认**：只用平均成本；完整账户收益包含现金及资金进出；成本期初确认一次，后续由买卖和费用更新；全账户统一统计、手工市值形成观察点、操作与代码简洁。
- **当前设计**：平均成本负责持仓与卖出盈亏，净值/份额负责累计账户收益率；期初持仓成本浮盈与自建档账户收益分别展示。累计收益率不能乘当前资产换算累计利润，新增资金通过份额参与后续计算。
- **统一业务入口与计算**：账户与数据负责编辑，持仓与标的详情负责展示；可添加复用表单的快捷入口，所有页面调用同一后端服务。期初、成交、独立资金事项及报价为事实，持仓和收益快照为派生结果。
- **完整交付闭环**：初始建档 → 买卖 → 资金 → 市值更新 → 持仓/现金/盈亏/曲线一致更新。内部开发可按依赖顺序推进，不以旧 S-001 阶段或独立收益录入作为产品分期。
- **事实与质量边界**：外币按币种保存，汇率保留实际时间；资金发生时缺少报价可估算并标注，补录后重算；未知状态不按零值。既有资料保留为来源，规范建档前缺失的历史利润不编造。
- **轻量维护**：保留 React/Vite、FastAPI、SQLite，普通 ID/时间/source 即可；不建立哈希版本链、泛化事件平台、复杂队列或新增 Agent 工作流。
